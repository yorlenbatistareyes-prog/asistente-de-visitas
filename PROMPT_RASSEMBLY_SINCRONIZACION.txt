PROMPT PARA CONSTRUIR LA SINCRONIZACION AUTOMATICA DE RASSEMBLY

Actua como arquitecto senior de una aplicacion Tauri + SvelteKit. Necesito implementar en RAssembly dos metodos de sincronizacion automatica completamente independientes:

1. Sincronizacion web mediante un servidor HTTP/HTTPS.
2. Sincronizacion mediante una carpeta compartida de Google Drive, OneDrive o cualquier carpeta local sincronizada.

REGLA PRINCIPAL E INNEGOCIABLE

Los dos metodos deben funcionar de manera independiente. No deben compartir servicios, funciones de subida, funciones de descarga, estados, temporizadores, banderas, claves de cifrado ni logica de deteccion de conflictos.

Solo pueden compartir:

- Tipos de datos generales y constantes puramente neutrales.
- Funciones de acceso a la base de datos que no sepan nada de sincronizacion.
- Una interfaz visual generica para mostrar estados, si esa interfaz recibe datos ya preparados.

No crees un mega-store combinado ni una funcion generica que decida entre web y carpeta. Cada carril debe poder probarse, depurarse, activarse o desactivarse sin afectar al otro.

CONTEXTO TECNICO

La aplicacion es una app de escritorio/movil con Tauri y SvelteKit. La base de datos local es SQLite. El frontend usa TypeScript y Svelte. El backend Tauri usa Rust.

La base de datos debe seguir siendo la fuente local de verdad. La sincronizacion no debe escribir archivos SQLite directamente desde el frontend mientras la base de datos esta abierta.

OBJETIVOS FUNCIONALES

- El usuario puede elegir un unico metodo activo: web, carpeta o ninguno.
- Si el metodo elegido es web, solo funciona el carril web.
- Si el metodo elegido es carpeta, solo funciona el carril de carpeta.
- El carril no elegido no debe hacer peticiones, leer rutas, abrir archivos, generar claves ni modificar su estado.
- Los cambios locales deben programar una subida con debounce.
- Al arrancar, volver del segundo plano o recuperar el foco, debe ejecutarse una comprobacion ligera.
- Si el remoto tiene una version mas nueva, debe mostrarse un conflicto antes de sobrescribir datos.
- Descargar debe reemplazar o restaurar los datos de forma atomica y conservar la marca de sincronizacion.
- Forzar subida debe sobrescribir el remoto solo despues de confirmacion explicita del usuario.
- Los errores deben mostrar el mensaje tecnico util en consola y un mensaje seguro y comprensible en la interfaz.
- Ninguna restauracion debe dejar la app en blanco ni abrir un bucle infinito de conflictos.

CONTRATO DEL SERVIDOR WEB

Implementar endpoints equivalentes a:

- POST /api/auth/request-code.
- POST /api/auth/verify-code.

- GET /api/apps/{appId}/backup.

El servidor debe devolver y validar:

- schema_version.
- revision_id monotonicamente creciente.
- backup_id.
- device_id.
- updated_at UTC generado en servidor.
- content_hash.

La subida debe usar control de concurrencia. Rechazar una subida si el cliente envia una revision base antigua, salvo que el usuario haya escogido forzar la subida.

Nunca incrustar en el frontend un token administrativo del servidor. Usar autenticacion del usuario y variables de entorno en el backend.

ALGORITMO DE SINCRONIZACION WEB

1. Un cambio local dispara un debounce de varios segundos.
2. Comprobar sesion y token.
3. Leer last_web_revision local.
4. Consultar el estado remoto.
5. Si remoto.revision_id es mayor que local, crear conflicto y no subir.
6. Si no hay conflicto, preparar datos desde SQLite.
7. Generar content_hash.
8. Subir con la revision base esperada.
9. Si el servidor confirma, guardar last_web_revision y metadatos web.
10. Si ocurre un cambio durante la subida, ejecutar una nueva subida despues de terminar.
11. Si falla, conservar el estado de error y permitir reintento.

ALGORITMO DE SINCRONIZACION POR CARPETA

1. Un cambio local dispara un debounce independiente.
2. Validar que existe una carpeta configurada.
3. Obtener o crear la clave exclusiva de carpeta.
4. Crear una instantanea SQLite consistente.
5. Validar la instantanea.
6. Crear metadata con revision, hash, dispositivo y hora UTC.
7. Cifrar un paquete autenticado.
8. Escribir a un archivo temporal dentro de la misma carpeta.
9. Cerrar el archivo, comprobar tamano y hash.
10. Reemplazar atomicamente sincronizacion_global.rassembly.
11. Guardar last_folder_revision y demas metadatos solo despues de que la escritura termine.
12. Si ocurre un cambio durante la subida, programar otra operacion despues de terminar.

ALGORITMO DE DETECCION DE CONFLICTO DE CARPETA

1. Leer el paquete compartido y sus metadatos, sin restaurarlo todavia.
2. Validar autenticidad y app_id.
3. Leer last_folder_revision y last_folder_content_hash locales.
4. Si el hash o revision remoto son nuevos, mostrar conflicto.
5. No depender unicamente del mtime, porque Google Drive y OneDrive pueden alterar fechas o tardar en sincronizar.
6. Si el archivo aun se esta sincronizando o esta incompleto, reintentar con backoff y no sobrescribir la base local.
7. Solo despues de la decision del usuario ejecutar restauracion.

RESTAURACION SEGURA

Para web:

- Descargar y validar el envelope.
- Restaurar dentro de una transaccion o mediante tablas temporales.
- Validar relaciones y esquema.
- Guardar last_web_revision en la misma operacion logica.
- Reactivar el radar despues de terminar.

Para carpeta:

- Descargar y descifrar a un archivo temporal.
- Validar que SQLite puede abrirlo y que contiene el esquema esperado.
- Guardar last_folder_revision dentro de la BD restaurada o en metadatos persistentes fuera de la BD.
- Cerrar conexiones de la BD actual.
- Aplicar el archivo pendiente una sola vez.
- Eliminar -wal y -shm de la BD antigua solo cuando corresponda.
- Renombrar de forma comprobada.
- Si hay reinicio, no guardar la marca solo en memoria ni en una BD que despues sera reemplazada.
- Tras iniciar, verificar que la version restaurada es la esperada antes de activar el radar.

ERRORES QUE DEBES EVITAR

- Leer SQLite directamente con fs.read mientras puede existir -wal.
- Escribir av_database.db desde el frontend mientras el plugin SQLite la tiene abierta.
- Usar el mismo last_synced_at para dos metodos independientes.
- Usar un unico temporizador o una unica bandera de sincronizacion.
- Comparar solamente fechas de archivos.
- Ignorar errores con let _ = en operaciones de reemplazo.
- Reiniciar antes de terminar de guardar metadatos.
- Guardar metadatos en la BD vieja y luego reemplazarla con otra BD.
- Dejar pending_restore despues de un fallo parcial.
- Ocultar el error real y mostrar solamente Error 500.
- Mantener un listener global que se registre varias veces con HMR.
- Permitir que el radar lance una subida mientras se esta restaurando.
- Hardcodear tokens privados en el cliente.
- Hacer que el metodo web importe codigo del metodo carpeta o viceversa.

CRITERIO DE ACEPTACION

No des por terminada la implementacion solo porque compila. Debes demostrar:

1. El metodo web funciona si el carril de carpeta esta roto o sin configurar.
2. El metodo carpeta funciona si el servidor web esta caido o no hay sesion.
3. Un conflicto se muestra una sola vez y desaparece al resolverlo.
4. La restauracion no vuelve a generar el mismo conflicto despues de reiniciar.
5. La configuracion abre despues de subir, descargar y pulsar F5.
6. Los datos SQLite restaurados se pueden leer inmediatamente.
7. Los errores contienen una causa identificable.
8. cargo check, pnpm check y las pruebas automatizadas pasan.
9. No existen dependencias de importacion entre webSyncService y folderSyncService.
10. Cada metodo puede desactivarse sin modificar la logica interna del otro.

FORMA DE TRABAJAR

Antes de editar:

- Inspecciona la estructura real del proyecto.
- Identifica como se inicializa SQLite.
- Identifica como se registra y se cierra la sesion.
- Identifica todos los listeners de cambios locales.
- No inventes nombres de tablas ni APIs que no existan.

Despues de cada cambio:

- Ejecuta la comprobacion mas cercana al archivo modificado.
- Ejecuta cargo check si cambia Rust.
- Ejecuta pnpm check si cambia Svelte o TypeScript.
- Ejecuta pruebas del carril afectado.
- Revisa que no hayas creado una dependencia entre carriles.
- No ocultes errores ni declares que esta terminado sin una prueba reproducible.
